# UTC Hack - January 2026 Ledger

## Architectural Decisions

### 2026-01-21: Temporal API Adoption for Timezone Conversion

**Context:** The original manual timezone offset math was broken and couldn't handle DST transitions correctly. The app was using incorrect calculations (30-day months, 365.25-year approximations) and had a Z-suffix appending bug.

**Decision:** Adopted `@js-temporal/polyfill` for all timezone conversions with strict validation and explicit DST disambiguation.

**Rationale:**

- Temporal API handles DST gaps and overlaps correctly
- Eliminates manual offset math errors
- Provides clear disambiguation options (reject, compatible, earlier, later)
- Uses Jan 15 vs Jul 15 offset comparison for DST detection
- Industry standard approach for timezone handling

**Implementation:**

- Created `src/timeConversion.ts` with strict validation
- toLocal: MUST have Z or offset (instant input)
- toUTC: MUST NOT have Z or offset (local wall time)
- Server returns 400 for validation violations

### 2026-01-21: 24-Hour Time Format Throughout

**Context:** User requirement to display all times in 24-hour format without AM/PM indicators.

**Decision:** Implemented 24-hour time format across all UI components and formatters.

**Rationale:**

- User preference for aviation/military time format
- Eliminates AM/PM ambiguity
- Consistent with international standards
- Custom spinner widget required to replace native datetime-local picker

**Implementation:**

- All formatters use `hour12: false`
- Custom time spinner widget for consistent 24-hour display
- UTC methods throughout (getUTCHours, getUTCMinutes, etc.)

### 2026-01-21: Strict Input Validation Pattern

**Context:** Need to prevent common timezone conversion errors where users provide wrong input format.

**Decision:** Implemented strict validation with clear error messages for input format violations.

**Rationale:**

- Prevents silent failures from incorrect input
- Makes API contract explicit and enforceable
- Catches errors early at validation layer
- Clear error messages guide correct usage

**Validation Rules:**

- UTC → Local: time MUST include Z or offset
- Local → UTC: time MUST NOT include Z or offset
- Violations return 400 with descriptive error

### 2026-01-21: In-Memory Caching with TTL

**Context:** Nominatim geocoding API has rate limits and external dependencies. Need to reduce API load while maintaining fresh data.

**Decision:** Implemented in-memory caching with different TTLs for different data types.

**Rationale:**

- Reduces external API calls
- Improves response time for repeated queries
- Graceful degradation if Nominatim unavailable
- Geocoding data doesn't change frequently (12h acceptable)
- Airport data even more stable (24h acceptable)

**Implementation:**

- Geocoding cache: 12-hour TTL
- Airport lookups: 24-hour TTL
- Retry/backoff for API failures
- Error types: rate_limited (429), upstream_unavailable (503)

### 2026-01-21: DST Disambiguation Strategy

**Context:** DST transitions create ambiguous wall times (gaps in spring, overlaps in fall). Need explicit handling strategy.

**Decision:** Default to "reject" for DST ambiguity, require explicit user choice for overlap scenarios.

**Rationale:**

- Safety first: rejecting ambiguous times prevents silent errors
- Forces user to acknowledge DST transition
- Compatible mode available for spring gaps (advances time forward)
- Earlier/later modes available for fall overlaps (explicit choice)
- Clear UI feedback for disambiguation requirement

**Implementation:**

- Gap (spring-forward): reject=error, compatible=advance forward
- Overlap (fall-back): earlier=first occurrence, later=second occurrence
- Default: reject (requires explicit handling)
- Disambiguation dropdown visible only for LOCAL → UTC

### 2026-01-21: Socket-Free Testing Pattern

**Context:** Need comprehensive API testing without port binding conflicts or async cleanup issues.

**Decision:** Implemented socket-free testing using supertest's app injection pattern.

**Rationale:**

- Tests run faster without actual port binding
- No cleanup issues with open sockets
- No port conflicts in CI/CD environments
- Tests focus on logic, not networking

**Implementation:**

- 6 integration tests in `src/server.test.ts`
- supertest handles app lifecycle
- No `.listen()` calls in test environment

## Technology Choices

### Core Stack

- **Runtime:** Node.js with TypeScript
- **Framework:** Express.js REST API
- **Timezone Library:** @js-temporal/polyfill
- **Testing:** Jest + supertest
- **Geocoding:** Nominatim API
- **Frontend:** Vanilla JavaScript with custom components

### Production Dependencies

- @js-temporal/polyfill - Correct DST handling
- express - HTTP server
- node-fetch - API requests
- cors - Cross-origin support

### Development Dependencies

- TypeScript + ts-node
- Jest + ts-jest
- supertest - API testing
- @types packages
